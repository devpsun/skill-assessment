## 使用流程

### 发起评测

1. 使用者安装工具，将包内配套 Skill 安装到宿主 Agent 的技能目录；自定义目录可指定。
2. 用户在宿主 Agent 中指定本地目标 Skill，要求评测。
3. 配套 Skill 指导宿主 Agent 阅读目标能力；若缺少 eval，则生成可检查的用例和评分标准，并保留生成来源。没有用例时，CLI 不自行调用模型猜测测试目标。
4. CLI 校验目标 Skill 和 eval 配置。静态错误阻止动态执行，同时生成可供修复的结构化结果；警告默认不阻断。
5. CLI 准备每个用例的独立工作区，安装该次测试声明的 Skill，调用配置的执行器，采集结果与产物。
6. 按用例声明评分并生成报告。宿主 Agent 总结结果和证据，等待用户下一步指示。

静态校验也可以单独运行，不需要安装 Agent 或连接模型。用例生成修改 eval 文件；评测执行修改工作区和报告；演进修改目标 Skill，这三个行为应在使用说明中明确。

### 用户主动要求改进

1. 宿主 Agent 读取用户指定的运行报告及失败证据。
2. 区分 Skill 缺陷、测试问题、运行环境问题和评分问题；原因不确定时保留不确定性。
3. 按用户要求修改目标 Skill 或有问题的 eval，并记录修改原因、内容差异和父运行标识。
4. 先回归相关失败用例，再运行完整测试集；补充新用例不代替旧用例回归。
5. 展示前后结果。用例或评分标准发生变化时单独标记，不能把不可比结果解释为质量提升。

实现有界的、由宿主对话驱动的改进能力。首版不引入后台自主进化进程；不以放宽有效断言使测试通过。

首版采用本地工作目录管理。该目录不是操作系统安全沙箱，不能宣称能安全执行任意不可信代码。

## 质量报告的口径

- 静态问题分为规格错误、工程检查与质量建议，记录规则来源与版本。
- 功能结果、执行错误、评分错误、跳过、取消分别统计。未测、证据缺失或无法判断不能记为通过。
- 基础展示包含计划试验数、实际执行数、各状态数量、有效评分通过率及评分覆盖率，显示分母。
- 耗时记录墙钟时间；Token/费用仅在 Agent 提供时记录，缺失为 unknown/null，不能填 0 冒充观测值。
- 有／无 Skill 对照使用相同输入、fixtures、执行配置和评分标准；只改变目标 Skill 的提供方式。不能控制外部服务时注明限制。
- 自然触发与功能效果需要区分：通过不证明 Skill 确实被加载；只有执行器提供相应证据时才记录触发结论。
- 重复运行展示通过次数和样本量；首版不宣称少量样本能证明跨模型一致性。
- 默认不计算未经定义权重的综合质量分，不给出“生产就绪”或“安全认证”结论。

## 暂缓范围

远程 HTTP 执行器、Docker/OpenSandbox、额外内置 Agent、复杂多轮用例、批量调度和仪表盘留待后续。Linux x86_64 / ARM64 构建验证、Windows/Linux CI 和 JUnit 已提前纳入当前实现。Linux 范围目前为 Ubuntu/glibc，不代表其他发行版或 32 位架构已验收。

参考 skill-up 的能力与组织方式。v0.1 不承诺完整读取 skill-up 配置、报告或 Anthropic evals.json；正式导入器另设兼容矩阵。当前没有用户存量配置迁移要求。
