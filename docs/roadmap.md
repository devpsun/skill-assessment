# 阶段计划与验收

状态：P0 基线。v0.1 是 P1 至 P4 完成后的首个 Windows 可用版本。阶段完成以验证证据为准，不以目录或接口存在为准；当前状态见 [进度](progress.md)。

## 阶段与依赖

| 阶段 | 目标 | 完成后可以做什么 |
| --- | --- | --- |
| P0 | 需求、架构、决策、验收及协作基线 | 根据仓库文档持续开发，不重复澄清已确定约束。 |
| P1 | Python/npm 分发和 Windows Agent 调用验证 | 从 tgz 安装最小 CLI，离线初始化，启动已配置的真实 Agent。 |
| P2 | 静态检查与 eval 配置 | 独立检查 Skill；校验并列出可执行用例。 |
| P3 | 执行、规则/脚本评分和结构化报告 | 运行单轮用例，归档证据，重建基本报告。 |
| P4 | 首版完整使用流程 | 通过配套 Skill 建例、评测、读报告，按需进行改进、重复及对照评测。 |
| P5 | Linux 与扩展执行器 | 验证 Linux 目标架构、构建分发，并按需求接入 HTTP Agent。 |
| P6 | CI/CD | 在 Windows/Linux runner 非交互执行，输出流水线可用状态及 JUnit。 |

P1-P4 可以按可独立验证的小步 PR 推进；真实 Windows 验收未完成时，平台支持状态保持“待验证”。P5 与 P6 的低优先级不取消首版需要的本地测试。

## P0：设计基线

- 交付：README、需求、架构、工程决策、参考版本、路线图、进度与 AGENTS.md。
- 验证：相对链接可解析；需求编号与验收场景可追踪；已确认约束与工程默认值分开；设计内容不冒充已实现能力。
- 退出条件：上述文件进入可审阅的独立分支/PR，足以开始 P1 的有限技术验证。后续实现不需要用户再次提供模型服务配置。

## P1：Windows 安装和调用技术验证

建议拆为两个 PR：Python/启动基础；npm 离线包与进程调用验证。

交付内容：

1. `pyproject.toml`、Python 包入口、`--version` 和 doctor 的最小实现。
2. npm launcher、首次启动 bootstrap、Python 路径选择、专用环境标识与重建。
3. Python 构建脚本，输出含完整离线依赖的 npm tgz；包内容白名单、依赖清单与版本一致性检查。
4. 包内资源定位和目标目录复制机制，为后续配套 Skill 安装做准备。
5. 执行器进程层技术验证：exe / npm cmd shim、stdin/文件输入、结构化输出、超时与子进程回收。

验收：在 Python 3.12 候选基线和目标 Windows x64 上，从新目录安装 tgz，首次运行禁止外部依赖请求；连续启动、重装、中文/空格路径均可用。实际安装版本、网络观测方式和日志脱敏后附于 PR。调用已配置 Claude Code 完成简单任务，不修改用户认证及模型配置。对应 A01、A06 的基础部分。

若本轮开发环境仅有 Linux，可完成静态检查、Linux 安装验证与可运行的 Windows 验证脚本，但不得关闭 Windows 真实 Agent 验收项。无需为验证工具进程协议而消耗真实模型调用。

## P2：静态检查与配置

建议拆为两个 PR：静态规则；eval/case schema 和命令。

- 建立规则注册、稳定编号、位置与来源；区分规范、工程检查及建议，固定规则基线。
- 为元数据类型、重复键、编码、Unicode 命名、大小写目录匹配、可识别链接与未知扩展字段建立代表样例。
- 交付 `check`、`validate`、`list-cases`；为 JSON stdout 与退出码定义可验证行为。
- 明确 eval 相对路径、fixture 文件、评分脚本及用例 ID 规则；错误消息包含定位。
- 验收 A02、A03 的校验部分；无 Agent 和无模型网络条件下通过检查测试。

静态错误是否阻断动态执行的完整验收在 P3 联调。检查正文链接不能误报代码块中的示例路径或尚未生成的目标产物。

## P3：评测主流程

建议拆为三个 PR：workspace/runner/协议；执行器；规则/脚本评分与结果归档。

- 固定输入快照和试验 ID；排除隐藏答案及评测代码进入测试 workspace。
- 交付 Claude Code 和通用本地命令适配器；公开协议 schema、接入说明和示例执行器。
- 用模拟执行器覆盖协议成功、失败、非法 JSON、超时、取消、缺失或越界产物等路径；模拟结果不作为真实模型效果证据。
- 交付规则断言、Python 脚本评分和版本化 result/manifest；保存事件、输出、评分及文件证据。
- 交付 `run`、JSON 和 Markdown 报告；`report` 读取归档重建阅读结果。
- 验收 A03-A06、A08 的核心流程；在真实 Windows Claude Code 上验证代表性 Skill，用具体安装版本记录结果。

同款 Agent 能否从宿主 Agent 中再次启动、全局 Skills 是否泄漏到试验、工具授权是否造成非交互阻塞，是此阶段必须验证的风险，不能仅通过模拟进程关闭。

## P4：完成 v0.1

建议拆为四个 PR：Agent 评分；复测与对照；HTML 报告；配套 Skill 与端到端样例。

- Agent 评分使用独立会话、固定 rubric 和结构化输出；评分失败不算功能失败或成功。
- 每次重跑生成新 run；提供用例选择、显式重复次数和有／无目标 Skill 对照。
- 验证 baseline 中没有目标 Skill 的可访问副本；条件不可控时标记对照无效。
- HTML 使用本地资源、相对产物引用及内容转义，能够移动目录后离线查看。
- 编写并随 npm 分发配套 Skill 与模板；仅依赖本地 CLI 和宿主文件/命令工具。
- 建例、评测、报告解读、用户主动要求后的改进是可区分的流程；改进保留父运行、变更原因和完整回归。
- 验收 A01-A10 全部场景；记录 Windows 实机证据、已支持版本及明确限制，之后才标记 v0.1 可发布。

v0.1 发布前确定内部 npm 名称、scope 和 registry 配置方式。公开源码不包含真实内部地址、凭据或业务数据。发布命令与构建命令独立，使用用户环境已有 npm 认证。

## P5：Linux 和后续能力

- 初始候选架构为 x86_64 与 ARM64/aarch64；若用户确需 x86 32 位或 ARMv7，另列平台目标，不能默认宣称已覆盖。
- 明确 Linux 发行版、glibc/其他 libc、Python/Node 版本及 Agent 安装版本，验证相应 wheel 和启动行为。
- 在对应环境构建、安装、评测；不假定 Windows 上生成的二进制依赖可跨平台使用。
- 根据实际接入需求实现 HTTP 自定义执行器；复用请求/响应模型，单独定义上传、下载、取消和远程产物归档。
- 复杂多轮、其他 Agent、导入 skill-up/Anthropic 配置和外部沙箱按实际需求分别规划。

## P6：CI/CD

交付非交互运行文档、稳定退出码、JUnit 报告和 Windows/Linux runner 示例；支持实际使用的流水线平台，不将 GitHub Actions 或 Linux Docker Action 作为唯一入口。模型可用性由流水线环境提供，配置通过已有 Agent 机制注入。

验证安装无额外外网下载、失败门禁、取消、产物保留及秘密信息不进入归档。发布自动化是独立任务，不将评测自动等同于发布。

## 验证记录格式

每个实现 PR 至少写明：目标行为、实际执行命令、OS/架构与相关版本、通过或失败结果、真实 Agent 与模拟执行器的区分、未执行项及原因。只为解决具体风险扩展测试；文档变更无需运行模型评测。
